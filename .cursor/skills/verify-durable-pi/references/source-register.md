## Verification layers

- **Source review:** Establishes implemented routes, controls, limits, and ownership. It does not establish a current deployed account/provider state.
- **Deterministic checks:** Exercise domain rules and adapters with isolated storage or synthetic responses. Read the named test before interpreting its coverage.
- **Native runtime checks:** Exercise actual Pi/SQLite/workerd boundaries, process interruption, and recovery, while external model/provider responses can still be synthetic.
- **Browser fixture:** Exercises the real frontend against synthetic auth/model/storage/transport responses. Real selectors and UI actions are meaningful; production persistence and provider acceptance remain unproved.
- **Real-model behavior:** Requires a real model to select the intended tools from a natural request, not a forced synthetic tool call.
- **Live provider acceptance:** Requires the actual inbox/provider message and corresponding Pi result, file, or decision record.

## Documentation decisions

1. Keep one user-journey directory in the pstack format. FEATURES.md is the product-facing index and surface matrix, not a second detailed behavior inventory.
2. Preserve useful ownership diagrams in docs/architecture.md. Implementation structure stays out of individual user recipes; this register carries source pointers.
3. Give each behavior a stable short ID. Give every feature entry points, prerequisites, actions, observable results, and Gotchas rather than a list of tool names alone.
4. Describe surface parity capability by capability. An ordinary agent retains its tools across channels, but interactive UI parity and participant routing are incomplete.
5. Separate implemented code from provider configuration and from evidence. WhatsApp live onboarding stays parked. This documentation work neither configures a provider nor creates an automation.
6. Reuse existing build, Playwright, native runtime, and acceptance harnesses. Add no product module, test-only public endpoint, scheduler, or wrapper CLI for the map.

## Consequential source finding

The WhatsApp inbound adapter validates only text/image/audio message types in `src/whatsapp/adapters/chat.ts`, and `WhatsAppMedia` in `src/whatsapp/contracts.ts` accepts image/audio MIME types. Its outbound export path accepts broader file MIME types. The map and README therefore distinguish document/video export from document/video intake. No product code was changed to close that gap.
