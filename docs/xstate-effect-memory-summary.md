# Memory summary lifecycle

B13 migrates summary admission, native requests, bounded correction, durable failure and explicit retry into official `@xstate/effect` machines. It preserves the existing summary algorithm, immutable originals and nodes, merge priority, source attribution, lineage, pinned model routes, and fifteen-request budget. Backup publication is the separate B18 lifecycle.

## Authority and ownership

`memory_ready.control` is the single versioned summary control record. `summary.machine.ts` owns queued, claimed, retry, paused and complete transitions. Its schema and workflow versions are both 1; unknown versions and malformed control fail validation. Legacy ready rows and their existing failure attempts/cooldowns convert in the same SQLite transaction. `memory_failures` is a transactionally maintained projection, not an independently writable control path. Completion inserts the immutable node, updates the existing tree/views and removes the ready/failure rows atomically.

A claim contains range, random token and control revision. Claim acquisition is atomic; concurrent pumps and newly constructed warm repositories cannot steal an active claim. Route binding, request admission, acknowledgement, failure and node publication validate the claim. Each new claim consumes one of three summary attempts. `next()` stays a selector and skips claims and paused work. Reads and normal wakeups cannot reset attempts.

The scoped compaction machine owns selection, concurrency admission, completion joins and the next wake projection. Effect owns its maximum eight native fibers. A claim remains owned through the complete joined native/actor scope, including cancellation cleanup. Only then can the durable machine accept completion, failure or uncertain pause. A warm exact persistence receipt survives a failed result/pause write and can be reconciled without another native call. The runner must use cleanup-only `reconcileSummaryReceipts` after an unsuccessful pump; `summaryNextWake` only projects discovery.

`restoreSummaryClaims()` is an explicit cold activation operation. It pauses orphan claims and fences their old tokens. Constructing a repository, displaying status or pumping a warm runtime never performs this restoration. The host must not call cold restoration while a warm native owner is still alive.

## Native request and retry policy

The request machine owns route capture, catalog validation, context budget, provider preparation, atomic debit, native dispatch and native success acknowledgement. It validates the current claim and pinned route immediately before dispatch. Existing `summary_routes.requests` remains the only request counter; request debit and `requestInFlight` commit together. A successful native return clears the in-flight flag before the correction machine can request again. The correction machine retains the existing five-response limit and 512-byte policy.

The production adapter intentionally continues to use pi-ai `completeSimple`, not a durable Pi submission. There is no durable native receipt from which an interrupted model response can be recovered. An admitted request whose result is unknown therefore pauses immediately without refund or automatic model replay. Timeout, cancellation, defect and orphan restoration likewise require explicit recovery. A confirmed empty or oversized response may use the remaining three-attempt/fifteen-request policy. Original messages remain available regardless of summary outcome.

Explicit retry retains the existing operation ID receipt and route revision fence. The retry machines inspect paused authority, resolve and validate current configuration, prearm finite Lifecycle discovery, and then recheck archive state, route revision, paused state and the admission deadline inside the shared native SQLite transaction. Only that commit resets the summary attempt budget and installs the new route revision. Applied operation replay skips configuration/catalog/discovery and never resets the route request debit. Commit, immediate wake and notification use an owned joined handoff scope.

## Failure-sensitive evidence

Actual SQLite characterization reproduced four concurrent production pumps dispatching the same range. Three failures paused it, explicit retry replaced route revision 1 with revision 2, and the original route-one call subsequently published a stale answer and cleared the issue. Durable claim fencing closes both paths.

Focused tests cover independent warm facades, native uncertainty across repeated status/pumps, request debit rollback, exact late result fencing after cold restore and explicit retry, three attempts and fifteen requests, legacy conversion and future version rejection, failed node publication followed by receipt-only reconciliation, held native cleanup, complete compound Cause retention, SQL-contention expiry, unavailable prearm and failed postcommit wake with retained discovery. The previous disposal assertions were changed deliberately: canceled work now leaves an actionable paused attempt rather than a ready row that could automatically call the model again.

Negative controls remove the durable claim fence, bypass retry prearm/deadline validation, and suppress late cleanup Cause retention. Each makes its corresponding behavioral assertion fail; the production implementation is restored afterward. Unit fixtures and synthetic native operations do not establish live-provider behavior or exactly-once model execution. Parent-owned runner integration and native restart gates supply the actual alarm and activation evidence.

## Native restart proof

Run `node scripts/test-memory-summary-runtime.mjs` with Node 24. The isolated fixture uses the installed workerd runtime, real Durable Object SQLite migrations, production summary machines, native completion adapter, routing and Lifecycle capability. Only the provider responses and storage-failure triggers are synthetic. It binds a random local port and uses a temporary persistence directory. It makes no external provider requests.

The proof kills workerd with SIGKILL, restarts it against the same disk, and waits without calling the object. Its retained native alarm completes previously admitted queued work and pauses an interrupted native request. The original source/provenance, claim, route revision and request debit remain intact. An ordinary wake cannot replay the request; explicit retry creates a new fenced claim and route authority, and replaying the same retry operation cannot reset that budget. A late result from the retired claim is rejected.

Actual oversized completions consume three claims and fifteen requests before pausing. A node-write outage uses one model request, then the installed SDK's three failure callbacks (one dispatch and two cleanup-only settlements); after the exhausted SDK pump row has actually been deleted, explicit scheduler recovery publishes the warm retained result without another model call. A separate preclaim storage failure retains a controller diagnostic without changing the queued summary. Restart and repeated ordinary wakes preserve this exhaustion, while explicit controller recovery creates a fresh epoch and a stale callback cannot replace its native owner. Held native disposal stays claimed until cleanup joins, then pauses while retaining the full cleanup defect. A later restart preserves all completed results and request counts.

The scheduler's three-callback bound is the installed SDK retry-episode policy. A kill before its exhausted diagnostic commits may repeat a read-only preclaim scan. This is separate from durable summary claim/request budgets: admitted native work always restores to paused uncertainty without automatic replay. Warm joined result receipts are in memory; losing that memory requires explicit summary recovery instead of reconstructing an unknown result.

`node scripts/test-memory-summary-runtime.mjs --break-uncertainty` mutates only the temporary bundle, changing cold restoration from pause to retry. It must exit unsuccessfully at the same cold-uncertainty assertion: the unsafe machine returns to claimed instead of paused. The source tree is unchanged by the negative control. This local proof does not establish live-provider behavior or exactly-once external model execution.

## Composed admission and review corrections

Conversation archival now prearms both summary and backup discovery before entering the existing shared SQLite transaction. Inside the acquired coordinator it checks both finite leases before appending new originals. An exact source replay, or cleanup that appends no new source, does not require new admission; the existing indexed source ledger supplies that distinction. No second journal or asynchronous authorization inside the transaction is introduced. The Routines native fixture uses an explicit synthetic maintenance lease solely to exercise its own journal path; the dedicated Memory fixtures prove actual retained discovery.

Independent shutdown review reproduced cleanup-only settlement escaping disposal. The runner now retains and joins that complete callback and prevents duplicate same-token settlement. A subsequent cold controller-read outage reproduced overwriting an already persisted recovery epoch and retired token. Terminal handling now propagates the unavailable read and writes no guessed replacement. The unchanged installed-Lifecycle/Node-SQLite reproduction passes with four failed reads, zero writes and the complete old marker preserved. This is distinct from the actual workerd alarm proof.
