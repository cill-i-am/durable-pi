# Activity controls and query lifetimes

F14 moves the Activity workbench's command and query lifetimes into scoped official `@xstate/effect` actors. Backend task, plan, mailbox and Pi records remain authoritative. The UI does not infer successful remote cancellation from an HTTP acknowledgement or start remote work when it mounts.

## Command ownership

`task-control.machine.ts` owns restoration, admission, preparation, submission and explicit recovery for background group controls and delegated child controls. One owner covers conflicting actions on the exact agent, group, child and endpoint prefix. Duplicate activations queue behind the same actor and cannot create another operation ID while preparation or HTTP work is occupied. New identities are generated only after admission, persisted before dispatch, and retained after an uncertain response.

The existing session-storage keys and unversioned command records remain compatible. A saved steering command keeps its original text and operation ID. Restoration only reads; it never posts. Explicit retry reuses the saved immutable command. A definitive backend rejection or successful acknowledgement removes only the matching saved operation. A late acknowledgement cannot remove a newer stored operation. Malformed, mismatched or explicitly versioned unknown records fail closed with recovery instructions and remain stored.

HTTP work is exclusive while pending. Once a steering or connection retry settles uncertain, an explicit Stop remains available as an independent obligation. It gets its own operation identity and preserves the earlier uncertain command. The same action's retry continues to use its original identity. There is no automatic command retry, transport retry loop or browser-created replacement for a backend attempt.

`mailbox-control.machine.ts` owns the shared mailbox control request. Admission validates the current task, delivery or scheduler epoch and agent. `retry_mailbox` sends the exact visible epoch; result retry sends the existing task identity, and delivery retry sends the existing envelope identity. A stale response cannot replace or clear a newer diagnosis. A 409 error remains visible. After an uncertain recovery response, explicit cancellation can target another eligible task using that task's identity; it never resends the previous recovery request by accident.

The owners use Effect scopes and the shared Activity native request boundary. Unmount or identity change revokes publication, aborts local requests and joins their actual settlement. It does not imply that the server rejected a command or that remote work stopped. Late compound checked failures, defects and original interruption reasons retain their annotations; finalizer failures use the repository's `fatalCause` representation. An uncertain task command remains in session storage throughout cleanup. A failure already stored in actor context is still retained by the owner finalizer: snapshot projection does not propagate that failure to the parent scope. This applies both to naturally settled Fail+Interrupt and Fail+Die+Interrupt responses and to late failures after abort.

`background-actions.tsx`, `bot-tasks.tsx` and `delegated-work.tsx` project these owners. Remote Stop pending/unconfirmed labels, retained output and backend delivery status remain read projections. A successful control response requests a new observation where applicable; it does not label the task stopped or the connection restored.

## Query ownership

`query.machine.ts` owns initial/manual reads, reading, waiting, hidden observation, settled history and fatal failure. `use-activity-query.ts` owns one Effect scope per complete semantic query key and enabled state. Keys include agent and every endpoint parameter. Each owner captures its read capability once; old owners cannot read a successor endpoint or publish under a new selection. Requests and cleanup remain owned until settlement.

Explicit refreshes during polling coalesce into one successor read. Duplicate history requests are ignored while occupied. Polling pauses while hidden and resumes on visibility; saved terminal conversations settle without more automatic polling. Ordinary transport/decoded read failures retain the existing visible reconnect cadence, with no new failure-count cutoff. Fatal compound failures require explicit refresh. Query retry creates no business-action authority.

The existing cadences remain: plans and model activity 2.5 seconds; activity list 5 seconds for latest and 15 seconds for a cursor; saved record 3 seconds; delegated list/latest transcript 2 seconds and older transcript 10 seconds; mailbox 3 seconds. History pagination remains explicit. Initial plan detail and every plan-history row must match the selected plan identity before publication, including later PlanInspector pages. A schema-valid response for another plan is rejected. `usePlans` joins list/detail/access observation, aborting siblings after the first failure and waiting for all siblings to settle.

The query migration covers `use-plans.ts`, `activity-timeline.tsx`, `activity-record.tsx`, `run-timeline.tsx`, `inference-runs.tsx`, PlanInspector history in `activity-workbench.tsx`, and the delegated/mailbox reads. DTOs, history-page merging, event views, elapsed/usage calculations, selections and form text remain pure projections or ordinary UI values. No durable browser machine snapshot, journal or SDK scheduler is added.

## Behavioral evidence and limits

The original built workbench admitted two same-task Retry connection activations before React rerendered, sent two distinct operation IDs and retained only the second. The new actor regression exercises that same boundary and verifies one request, one saved identity and exact explicit retry. Actor tests also cover compatible restoration, corrupt/future records, stale acknowledgements, authority revocation during preparation, malformed events, held native cleanup, exact mailbox epochs and independent Stop after uncertain steering.

The query characterization mounted the real `usePlans` and `RunTimeline`: an online event overlapped the first plans request, unmount did not abort it, and an older-page response could publish under a newly selected run. Retained browser assertions cover these boundaries. Focused native tests cover joined sibling/body cleanup, ApiError codes, more than five ordinary failures, hidden/terminal observations and full late compound Causes. A bundle-only negative control removes late-Cause retention and must fail the corresponding assertion; another removes mailbox epoch admission and must fail the stale-epoch assertion.

`tests/browser/activity-controls-lifecycle.spec.ts` exercises the actual built workbench on desktop and mobile with synthetic APIs. It checks duplicate admission, lost acknowledgements and exact saved retry, legacy steering across reload, independent Stop availability, retained output and unconfirmed remote-stop labels. `communication-recovery.spec.ts` covers result/mailbox recovery, disabled pending controls, retained outcomes and stale diagnostic responses. These are local browser and resource-ownership proofs. They do not prove live provider delivery, real-model behavior, deployment or broad repository completion. Integrated static and full repository gates remain separately owned.
