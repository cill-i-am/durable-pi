## Control ownership, exhaustion and Stop

A control claim persists a unique owner, deadline and attempt count against the current root/revision. Observation is bounded at sixty seconds per control pass. Automatic control has a three-attempt failure budget before actionable uncertainty. These are transport/control budgets, not limits on Pi execution or a person's approval wait. An ordinary wake, replay or inspection without a confirmed final result cannot renew exhausted automatic control. Consequential native dispatch rechecks current authority; existing accepted native receipts are reconciled using their original request identity.

An owner remains occupied until its Effect actor scope has joined acquired resources and native cleanup. Session acquisition binds a late acquired session before interruption can leave it orphaned. A timeout or local abort wait ending is not proof that the native task settled. Fail, Die, Interrupt and late cleanup Causes survive the scope boundary, including a concurrent persistence failure.

After cleanup joins, the warm pump retains an exact completed-release receipt containing root, owner, confirmation and release outcome. If persisting release fails, reconciliation retries that receipt before another claim. It never steals a live owner because its deadline elapsed. Cold restoration lacks that warm cleanup proof and preserves uncertainty for unfinished owned work. Release, exhaustion and native completion are fenced so an old owner or revision cannot settle newer work.

First Stop durably revokes future execution and access in the existing shared transaction. It attempts discovery first, but failed or interrupted prearm cannot prevent the revocation commit; scheduling failure is preserved and Stop is recorded as unconfirmed. A fresh lease gives Stop its own bounded recovery budget even when handoff/observation was exhausted. If another control owner is still live, Stop keeps that owner: the same owner performs native abort or finishes joining before the next owner proceeds. A late failure from the preceding handoff cannot consume the fresh Stop budget.

Repeating first Stop does not reset that budget. `retryStop` requires a fresh discovery lease, the exact displayed revision, an unconfirmed stopping root and no live owner. It retains the original native identity. Family-authority loss still permits cleanup-only progression. Background report Stop remains part of its existing coupled transaction; this B06 record does not change the independent B03 background cancellation policy.

## Admission and durable discovery

Every new admission requires a fresh `discoveryDeadline` from `armDiscovery()` before the acceptance transaction. The final commit checks freshness with Effect's clock, immutable identity/content, current parent/authority, attachment ownership and configuration. Missing or expired discovery is a transient `ConversationStorageError` and rolls back the entire coupled transaction. Exact receipt replay is checked first: it may omit a lease, returns the existing receipt and cannot renew control attempts.

Apps, Routines, Communication continuations, Coordination resume messages and Background reports pass the same deadline through their actual admission callback. Their outbox consumption, delivery acknowledgement, continuation or report state still commits with the Conversations admission under the original transaction owner. Prearm and asynchronous preparation stay outside SQL callbacks; final revalidation stays inside. Postcommit wake remains an immediate notification. Its failure cannot erase the already persisted discovery lease or accepted intent.

`armDiscovery()` returns its own sixty-second lease after persisting discovery. Overlapping arms retain the maximum deadline and rotate a generation token. An early empty scan retains another scan through that deadline; time is captured before the awaited domain read so a slow scan cannot silently discard a concurrent admission. At expiry, discovered pending work wakes the pump. No second scheduler or direct `setAlarm` owner is introduced.

Pump and discovery jobs use versioned tokens. Old callbacks cannot dispatch or exhaust newer work; an old completion retains a newer same-ID job instead of letting the SDK delete it. Exhaustion rechecks both the token and the exact domain root/revision/phase inside the persistence transaction. Existing legacy payloadless pump jobs remain readable; future job formats/functions fail explicitly.

Lifecycle allows three attempts per dispatch with 100 ms base delay and 1,000 ms cap. Repeated wakes during a live or failed dispatch rearm without replacing its retry or renewing the domain budget. Successful completion honors a pending wake. Discovery can retain its original still-fresh lease after dispatch exhaustion, so three attempts is not a lifetime total across all discovery reschedules. Failure to persist exhaustion is logged without claiming a durable outcome or automatically renewing that pump dispatch. Cold reconciliation restores domain state once after success, validates/rearms existing jobs, and can rediscover eligible work when both jobs are absent.

Prearm/wake observation has an interruptible five-second timeout, including inside uninterruptible Stop. These scheduling calls own no local resource finalizers; late completion can add a redundant wake but cannot admit a turn or confirm Stop. Synchronous throws remain defects and compound Causes are retained. This bounded observation policy does not replace joined cleanup for native operations.

## Tool recovery and public recovery actions

Tool recovery retains the existing warning-after-three, stop-after-five and three recovery-attempt policy. It correlates native assistant/tool-result rounds, distinct invocation identities, result cursor, request epoch and Access receipt ownership before accepting observations. The first failing parallel round can offer feedback without retroactively charging calls that already ran. An immutable round-start budget and deduplicated invocation/result identities govern later recovery; replay cannot replenish it. Denial and uncertain external effects retain precedence over repetition recovery. State and changed-view history commit together; replay cannot duplicate history or reset exhausted recovery.

The native Stop hook receives the original Pi context for self-abort, preserving the native task's own cancellation semantics. It does not add another local cancellation owner. Historic blocked detail and execution receipts survive restoration; a successful tool result is progress, not proof that the complete request succeeded.

Public turn projections add optional revision, uncertainty and busy fields. Private owner tokens and attempt bookkeeping remain internal. The scoped [`recovery controls`](../src/features/conversation/recovery-controls.machine.ts) offer **Check reply**, and **Try Stop again** for uncertain Stop. Requests carry the displayed original operation ID and revision. Checking only observes/reconciles that existing execution; it neither submits another message nor renews automatic recovery. Stop recovery uses the guarded retry described above. Stale or busy commands fail rather than acting on a replacement turn.

An HTTP acknowledgement does not count as a newer authoritative snapshot. Successful controls stay disabled until revision/uncertainty changes; a failed request permits another explicit action. Component disposal joins request cleanup and preserves late failure. Older snapshots remain readable but cannot authorize revision-fenced recovery without the added fields. The initial actual-component desktop/mobile run reproduced a transport-refresh remount that discarded this acknowledgement fence. Retaining the last complete same-agent view now preserves the existing recovery owner until replacement metadata arrives. Agent changes, disabling the view and known access denials clear that retained projection. All six recovery browser cases pass: same-revision acknowledgement fencing, explicit Stop/cleanup, and a known 403 clearing saved content and controls. The complete browser gate remains separate.

## Final integration review: Stop remains actionable

The actual HTTP Stop route now handles revocation before attempting warm control-release reconciliation. A failed joined-release write can retain the previous owner, but cannot prevent the shared Conversation/Access transaction from recording Stop. The regression uses a real SQLite release-only trigger and the actual PersonalAgent route: before the fix, it returned 400 without revocation; afterward it returns 202, retains the same owner, cancels the approval and starts no native work. The release failure remains visible to later reconciliation.

Background report Stop now obtains its own Conversations discovery lease before entering the existing Background acceptance machine. The coupled cancellation transaction receives that lease separately from Background's cleanup deadline. A failed or expired Conversations arm still records group revocation and an unconfirmed report Stop; repeated ordinary Stop cannot renew the report's exhausted budget. The existing scoped command machine preserves the scheduling Cause. Scheduler-only observations remain bounded, while native cleanup remains joined.
