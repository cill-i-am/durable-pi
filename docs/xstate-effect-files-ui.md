# File and media browser lifecycles

**Release status — 25 October 2026:** the refactor is [merged, deployed and verified](xstate-effect-release.md). The checkpoints below retain their original source and test scope; pre-merge delivery status is historical.

F03 moves browser-owned progression into official scoped `@xstate/effect` actors. Backend file reservations, extraction jobs, file data, and composer draft persistence keep their existing owners. This change does not add a browser workflow journal or a Pi execution.

## Upload and file ownership

`useFiles(agentId, initialSelection)` retains its public API. One mounted agent owns `makeFilesOwner` and its Effect scope. A pure cache holds the agent's file list and selection; asynchronous work can reach only that cache. A different agent gets a different cache before its first request completes. Workspace ownership changes already remount the component subtree. Late results from an aborted former owner therefore cannot change the next owner's files or draft selection.

The batch machine admits one upload batch at a time. Each item runs its own checking, uploading, publishing, done or failed machine. The machine enforces the existing four-attachment admission limit and nonempty, at-most-eight-megabyte file limit. Uploads run sequentially. A duplicate command while occupied does not start another request. A failed item retains its `File`, attachment choice and reservation ID. Explicit Retry must reference that same failed item and content; it does not allocate a new reservation. There is no automatic upload retry.

The existing backend pending reservation lookup remains: choosing the matching name and size reuses its server ID. Within one chosen batch a reservation can be assigned only once. Successful publication removes only that attempt. Dismiss removes only failed attempts, and clearing a submitted message removes only its submitted selection IDs.

The file query machine owns reads and the two-second preparation observation timer. Reads serialize and refresh commands coalesce. A mutation or upload committed while a read is running marks that read obsolete. Its result cannot replace the newer cache; a fresh read follows. Observations continue every two seconds while extraction or video preparation is pending, including after transient read failures. A failed read retains the pending fact and visible error; the next successful authoritative read clears the error and determines whether polling is still needed. Explicit Refresh also requests a read. These reads never restart backend extraction. File mutations have their own single-request machine and preserve their existing endpoints and result decoding.

Effect owns the full fetch and response decoding promise through `nativeOperation`. Scope disposal signals abort and joins actual promise settlement. React unsubscribes immediately; it does not claim that abort reverses a server-side upload. The parent scope closes mutation and upload actors before closing the query actor they use for publication. Independent error actions clear display errors without resetting upload attempt identity or failed-attempt content.

## Voice recording and preview ownership

The voice machine admits capture, cancellation, finishing, release and upload. Cancelling a pending permission request keeps the control occupied until `getUserMedia` actually settles and every acquired track is released. A browser-local microphone permit spans acquisition, native recorder stop and track release, so mounting another agent cannot start a second acquisition while the former owner is still releasing. A failed release blocks that recorder instead of offering a premature restart. Permission denial returns to an actionable explicit retry.

Effect owns the stream, recorder callbacks and the final stop acknowledgement. Finishing waits for native `dataavailable` and `stop` before creating the `File`; cancellation never uploads the captured chunks. The existing MIME preference, one-second recorder chunks, eight-megabyte limit and ten-minute recording limit remain. The machine owns the ten-minute timer, which disappears on cancellation. The finished `File` uses the existing shared upload callback once. Reload remains guarded through acquisition, recording, release and upload, including a permission prompt that has not settled.

One scoped preview actor owns each text, transcript or video-frame request. Agent and resource changes clear the previous result immediately and fence its late completion; closing a pending transcript signals abort. Scope closure joins the entire fetch and response-decoding promise. Transcript reads retain the existing two-page bound and reject nonprogressing pagination. A failed transcript offers explicit retry by closing and reopening. Audio retains native browser controls and its authenticated source URL; replacement and unmount pause the former element, remove its source and reload it to release the media resource. Images and prepared video frames remain native image elements. These components create no object URLs.

The file-details machine owns viewing, editing and the pending mutation. It freezes the submitted name, suppresses repeated commands while occupied and retains an edit when the existing mutation API returns rejection. Agent/file keys prevent late mutation acknowledgement from changing the next editor. Transport and cache publication remain owned by `makeFilesOwner`.

The installed alpha.8 actor host can capture an interrupted invocation's failure without propagating it to the outer owner. `fileWorkFailures`, registered before the actors, observes Die-containing exits and reports their complete compound Cause after child cleanup has joined. This includes checked failure and interruption reasons accompanying a defect. Ordinary checked rejection after abort remains expected cancellation; it is not converted into a cleanup defect.

## Compatibility

These actors are ephemeral and no actor snapshot is persisted. The installed library versions remain Effect 4.0.5, XState 6.0.0-alpha.68 and `@xstate/effect` 1.0.0-alpha.8. There is no changed application persistence schema or stored workflow version to convert. Existing composer draft references and backend file/reservation IDs remain readable without a data migration. Browser `File` handles remain in the current mounted owner, as before; this work does not promise resumable byte streams across a reload. After reload the server reservation remains discoverable and reselecting its matching file uses the same ID.

`uploads.ts` retains its Promise API for the terminal export caller and accepts an optional abort signal. That caller's broader terminal lifecycle is outside F03. `preparation.ts`, attachment filtering, selected-file data, and file descriptions remain pure projections.

## Evidence and limits

The pre-change Chromium probe at `/private/tmp/f03-before` exercised the production hook and microphone component with held synthetic platform operations. Duplicate upload admission already produced one request. It also demonstrated a late alpha upload replacing beta's files and selection, and cancel/restart while microphone permission was unresolved producing two simultaneous acquisitions. Denied permission already returned an actionable error.

`tests/files-lifecycle.test.ts` covers duplicate admission, exact content/identity retry, malformed events, capacity and byte limits, serialized publication, obsolete read rejection, joined upload cleanup, mutation failures, and recovery after four transient observation failures at the unchanged two-second cadence. `tests/browser/files-lifecycle.spec.ts` bundles the actual production hook and actors into a minimal React host and runs in Chromium on desktop and mobile. It holds fetch after abort, verifies owner isolation, checks stable retry and backend reservation IDs, holds an obsolete list response through upload publication, and checks explicit error recovery.

The isolated browser-bundle control `F03_BREAK_REFRESH_FENCE=1` removes only the query's obsolete-result guard. The unchanged retention assertion fails with `files: []` after the old response returns; production source is never patched. Raw upload-lane logs are `/private/tmp/f03-unit.log`, `/private/tmp/f03-browser.log`, and `/private/tmp/f03-browser-negative.log`.

These proofs use synthetic fetch/media services and no live providers or user files. They establish browser ownership and cleanup boundaries, not hosted upload delivery. The existing workspace-file suite continues to cover backend file behavior. The parent integration gate runs the built application's file and media journeys against the final composed tree.

`tests/voice-recorder-machine.test.ts` and `tests/file-preview-machine.test.ts` add sixteen focused cases covering held permission, cross-owner microphone handoff, final native audio data, joined stop, failed track cleanup, denied permission, byte and time bounds, malformed events, stale previews, bounded transcript pagination, immutable rename submission and complete late cleanup Causes. `tests/browser/file-media-lifecycle.spec.ts` bundles the production components in an isolated React fixture and runs eight cases on desktop and mobile Chromium. It retains the original cancel/restart safety assertion, checks late preview and mutation completion across agent changes, and checks the native audio source belongs only to the current agent. The built-application `audio.spec.ts` reload case now waits for the late permission stream to be released before enabling Reload.

The media negative control `F03_NEGATIVE_RELEASE=1` removes only `track.stop()` from the browser bundle. The unchanged cancellation assertion fails with zero stopped tracks instead of one; production source is unchanged. Media evidence is retained in `/private/tmp/f03-media-unit-5.log`, `/private/tmp/f03-media-browser-final.log` and `/private/tmp/f03-media-browser-negative.log`. The media fixture holds synthetic recorder stop and final-data delivery; it does not claim live microphone permission, real encoding/playback or hosted provider delivery. Those platform capabilities remain native browser APIs, and the final composed application's existing audio journey is a separate integration gate.
