# Memory backup publication

B18 moves incremental publication, local retry admission, and detached alarm dispatch into explicit machines built through `@xstate/effect`. Existing SQLite facts and the existing R2 objects remain authoritative. The archive format, content hashes, page selection, and memory algorithms are unchanged.

## Authority and progression

`backup-publication.machine.ts` owns `loading → paging → uploading → manifest → checkpointing → publishing → settled`. It invokes Effect work inside an explicitly scoped actor. Each pass writes at most eight archive pages. An incomplete pass commits only `progress.json`; a complete pass joins the conditional progress write and immutable snapshot write before publishing `latest.json`.

The R2 adapter retains its existing conditional ETag/absent writes and joins actual native promises. The progress write uses the ETag read at admission. The latest write now also uses its observed ETag (or an absence condition). Both observed progress and latest watermarks are checked against the local snapshot before publication, so a publisher that reads an already newer latest cannot conditionally overwrite it with older data. Batches and snapshots keep their SHA-256 paths. If a restart finds a complete progress checkpoint for the same watermark and parts, it reuses that exact manifest, including its date, rather than minting another snapshot identity. The same immutable snapshot may be written again idempotently; its key and content are unchanged.

`backup.machine.ts` reconstructs from the existing `memory_backup_status` row. Its phases are `idle`, `pending`, `running`, and `failed`. A synchronous transaction validates the current record and event, decides the transition, and writes the result. The original `date`, `watermark`, and `error` remain the public projection. There is no separately writable machine snapshot.

The additional columns are `schema_version`, `workflow_version`, `phase`, `target`, `attempts`, `attempt_id`, and `retry_at`. Schema and workflow versions are independently `1`; migration 20 defaults both to `0` for historical rows. The adapter converts known `0/0` records transactionally, preserving all original facts. Partial/future versions and impossible running owners are rejected without rewriting the row. The remote manifest and batch formats remain version `1`; unknown remote versions fail before publication. There is no Pi task implementation version because this lifecycle does not submit Pi work. Library versions remain pinned by the repository standard and lockfile.

## Retry and resource ownership

An attempt durably claims the current local watermark before remote work. The exact attempt ID fences completion and terminal exhaustion. Three failed or interrupted attempts exhaust one watermark. Retryable transport/conflict failures wait ten seconds; a successful partial checkpoint resets consecutive failures and schedules continuation after 100 milliseconds. An ordinary wake, a new service facade, and cold restoration cannot renew an exhausted watermark. `retryMemoryBackup({ attemptId, target }, lease)` explicitly reopens only the matching failed owner after validating the retained lease inside the acquired SQL transaction; a changed local watermark admits a new budget. Invalid/ahead backup failures pause immediately with a repair message.

After publication, the application reads the local watermark again. A concurrent local write leaves the just-published watermark as the completed fact and schedules another pass. It never labels the newer local state as backed up.

A semaphore shared by the SQLite transaction group holds the complete publication scope, including native R2/body cleanup. A newly constructed facade waits for that scope; it cannot mistake live work for an orphan. A cold `running` record consumes its already-recorded attempt when restored. `dispose()` signals cancellation and joins the actual producer, in-flight restoration, and terminal cleanup before its caller may dispose the Effect runtime or SQLite services. An alarm returning from restoration rechecks shutdown before admitting work. Late defects and checked failures remain in the complete Cause, including across a host Promise runner that would otherwise select only one error.

## Lifecycle adapter contract

`BackupRunner<E, R>` lives in `src/memory/adapters/backup-lifecycle.ts`. The production host provides:

- `run(work, { signal? })`: execute an Effect through the owned runtime and forward the cancellation signal.
- `step(onClaim)`: call `runMemoryBackup(prefix, onClaim)`.
- `restore()`: call `restoreMemoryBackup()`.
- `exhaust(claim, current)`: call `exhaustMemoryBackup(claim, current)`; the queue eligibility check runs inside the same SQLite transaction as the exact claim comparison.
- `retain(work)`: retain the detached producer through the Durable Object host.

The runtime supplies `MemoryRepository`, `MemoryBackupStatus`, `BackupStore`, and `Crypto`. The existing backup admission boundary is retained. Cold startup calls `reconcile()`. Ordinary admission calls `armDiscovery()` before committing new memory; it returns `{ deadline, current }` backed by `memory-backups:discovery`. Import prearms both summary and backup discovery, then validates both actual retained leases and the current Clock inside the shared SQL transaction. Failure, replacement, or expiry prevents publication. Empty pre-admission scans retain a wake for sixty seconds. Conversation journal admission uses the same host leases.

Explicit per-watermark retry first calls `armRecovery()`, which refuses to replace a live producer, an unsettled failed claim, or terminal cleanup and retains an empty scan through its deadline. Scheduler infrastructure exhaustion is separate: existing Lifecycle storage holds a versioned `memory-backups:failure` diagnostic with an exact recovery epoch, without fabricating a domain attempt. `recovery()`, `armSchedulerRecovery(epoch)`, and `retrySchedulerRecovery(epoch, lease)` expose its explicit repair path. Ordinary wakes and admission prearms cannot clear exhaustion. If discovery exhausts while a producer is live, its original pump keeps a heartbeat and recovery waits for native settlement. The diagnostic retains an exact claim, when present, independently of the queue row. A joined failed claim transfers to cleanup-only work after explicit recovery, including when Lifecycle already deleted the exhausted pump or final cleanup row. Only successful exact cleanup clears that receipt; ordinary domain retry cannot replace it. Known version 1 diagnostics without the optional claim remain readable. A failed controller read is never treated as an absent record: terminal handling preserves the unknown durable facts rather than writing a guessed replacement. If storage cannot read that authority, no new terminal marker can be promised until it recovers.

Both ordinary summary completion and receipt-only recovery replay notify, backup wake, and active-conversation wake even when the summary already committed. This closes the publication-to-handoff crash window using the retained summary queue obligation; the backup watermark makes repeated wakes harmless.

Cold startup calls `reconcile()`. Shutdown must await the backup runner before closing that runtime or its storage scope.

The adapter retains the historical `memory-backups:pump` ID and `pump` function. Payloadless historical jobs are accepted using a stable identity derived from their creation time; new payloads carry distinct schema/workflow versions and a token. Unknown versions fail before admission. Slow work runs outside alarm dispatch while the original queue row retains a thirty-second heartbeat. Ordinary wakes reschedule/rearm that row and preserve its budget. A wake received during work produces a subsequent observation.

`backup-dispatch.machine.ts` owns local idle/working/ready/failed progression. A failed dispatch keeps returning its same full Cause to Lifecycle; it does not start another successful heartbeat that would reset the SDK retry counter. Lifecycle receives a finite three-attempt transport budget. Terminal handling joins the producer and persists exhaustion for its exact receipt. If that persistence fails, one new finite three-attempt **cleanup-only** job may retry the receipt; it cannot call the backup provider. A stale cleanup cannot overwrite a replacement queue owner. Exhausting that final storage budget stops automatic work and records actionable scheduler recovery. If storage remains unavailable throughout, the last durable domain fact remains authoritative; the adapter cannot promise a terminal database write during an outage.

## Local evidence and limits

The focused five-file suite passes 82 tests: archive characterization, application behavior, native resource ownership, backup lifecycle, and runner behavior. The new tests use real SQLite migrations and the production memory/status/bucket adapters with synthetic bucket objects. They prove exact checkpoint identity after reconstruction, stale latest publication rejection, concurrent local-write bookkeeping, three-attempt exhaustion across facades, explicit retry, deadline preservation, legacy conversion, malformed events/versions, live-owner exclusion, and partial checkpoint failure joined with a late snapshot cleanup defect. Runner tests prove the literal legacy queue ID, retained identity, finite cleanup-only behavior, replacement fencing, full Causes, joined cancellation with late defects, queue-deletion recovery from a durable exact receipt, and disposal during held restore and cleanup.

Five production mutations were applied separately and restored in `finally`. Each failed its intended assertion:

| Removed behavior | Observed failure |
| --- | --- |
| Latest ETag/absence condition | Delayed old publication succeeded instead of failing, allowing stale latest data. |
| Three-attempt retry limit | Third failure remained pending instead of exhausted. |
| Complete checkpoint identity reuse | Restart produced a different manifest date and immutable snapshot identity. |
| Import deadline validation inside the transaction | Import committed after a retained lease expired while waiting for the SQL coordinator. |
| Live-owner check on explicit backup retry | Retry replaced the queue owner while the original native producer remained held. |

SDK transport attempts are the installed per-episode three-attempt budget. A killed preclaim scan can run again before any exhaustion marker commits; the adapter does not introduce a competing transport debit engine. An unabortable native promise must settle before warm ownership can be released; bounded retries do not imply a timeout for that foreign operation. This evidence uses synthetic data and local storage only: no hosted R2, providers, merge, or deployment. The historical native proof was run on the isolated Memory branch; the parent stack's composed native gate remains separate.
