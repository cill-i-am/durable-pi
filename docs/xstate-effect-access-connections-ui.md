# Approval and MCP connection frontend lifecycles

**Release status — 25 October 2026:** the refactor is [merged, deployed and verified](xstate-effect-release.md). The checkpoints below retain their original source and test scope; pre-merge delivery status is historical.

F06 moves approval decisions, tool-policy requests and connection catalog/mutation requests into feature-owned machines through the official `@xstate/effect` integration. The public Access and Connections APIs are unchanged. Access and the MCP SDK retain authorization and protocol authority.

## Invariants and ownership

- `approval.machine.ts` owns ready, submitting and uncertain decisions. An admitted request captures agent, action ID, turn, tool, exact input, creation/expiry, action revision and, for Always allow, policy revision. A completion cannot confirm another agent, action, input or revision. A changed policy cannot authorize replay of an older Always allow request. A late response can still confirm its action decision, but cannot claim future permission over a newer observed policy; later policy changes also remove that future-permission confirmation. Backend status still determines running, completed, denied, cancelled and expired presentation.
- `access.machine.ts` owns hidden, loading, ready, saving and failed observation. Policy changes use the revision displayed to the user. While saving, another write or reload cannot replace the request. A failed acknowledgement retains the last observed policy; it does not grant permission. Reload reads current backend authority.
- `connections.machine.ts` owns hidden, loading, ready, mutating, unavailable and uncertain observation. One actor serializes catalog refresh with connect, reconnect, refresh-tools, disconnect and per-agent selection. Superseded reads lose their invocation authority. A mutation is admitted only against the current catalog/selection revision and agent. Failed acknowledgements retain the exact action/body. An explicit identical retry can repeat that identity; a successful reload observes backend/SDK state before another explicit intent.
- Each mounted feature owns an Effect scope. Agent changes dispose the previous owner; projections and callbacks are fenced to that agent. Scope closure aborts HTTP observation and joins genuine foreign settlement. Cleanup defects and their complete compound Cause, including original interruption reasons and annotations, remain observable even after the actor mailbox closes. Leaving the UI does not revoke or reverse a server-accepted decision or connection operation.
- Buttons project machine occupancy. Conflicting controls stay disabled while a request is pending. After uncertain reconnect, the same reconnect and read-only Reload remain available; conflicting actions remain disabled. Add-connection retries keep the generated connection ID, name and endpoint. Draft text and callback banners are ordinary UI data; the SDK's statuses and authorization URL are read-only projections.

There is no automatic mutation retry, model request, OAuth exchange or permission grant in these frontend machines. Reopening settings and pressing Reload perform reads. Each explicit mutation makes one HTTP request. Backend revision checks and B17's connection lifecycle determine whether a repeated identity is a replay, conflict or newly authorized operation. Existing server records and IDs are preserved; these transient observers introduce no persisted browser snapshot or storage migration.

## Evidence

The pre-change projection regression in `tests/approval-decision.test.ts` failed because a confirmation for one action was accepted for another action or changed inputs. The retained regression now passes.

`tests/access-connections-ui.test.ts` exercises official actors with held Effects and foreign HTTP promises: stale action/agent/input/revision responses, policy-revision changes during uncertainty, conflicting decisions, malformed events, exact production HTTP payloads, serialization, old catalog completion, exact reconnect and add identity, SDK status projection, and joined late compound cleanup failures. Together with existing approval projection/presentation tests, the focused suite has 26 passing cases. The combined related gate adds Access coordination, Connections and MCP OAuth tests: 65 cases across six files pass.

`tests/browser/access-connections-lifecycle.spec.ts` runs the actual built application against synthetic read/mutation responses on desktop and mobile. It checks approval pending/uncertain controls and retained inputs, unconfirmed policy changes followed by authoritative reload, exact reconnect retries and SDK authorization status, stale catalog response fencing, and no page errors. The existing access browser journey remains included. The initial ten desktop/mobile cases passed. After independent review identified a late Always allow response overriding a newer deny projection, two additional desktop/mobile cases passed against the rebuilt repaired source. The local servers were cleaned up afterward. Full TypeScript checking, scoped architecture lint and formatting also pass.

Independent review also exposed original interruption reasons being dropped from joined compound cleanup. Retained regressions failed before both repairs and now pass for policy changes before and after acknowledgement and every original cleanup value and annotation across approval, policy and connections owners. The reviewer’s unchanged combined probe also passes.

Temporary Vite transforms removed the approval completion fence and reconnect identity comparison independently. Both corresponding regression tests failed at their behavioral assertions; the mutation sentinels confirmed the transforms ran. Production source was unchanged by these negative controls.

This is frontend lifecycle evidence, not a fresh native MCP/OAuth/provider delivery proof. The parent owns composed static, broad browser/native gates, publication and inventory updates. No live provider/account actions, package changes, Git writes, merge or deployment were performed in this slice.
