## Ownership and behavior

The existing `background_handoffs` row remains authoritative. No machine snapshot, second execution journal, replacement native identity or additional alarm owner was added. The handoff status describes report progression; `stop_state` independently records `none`, `pending`, `confirmed` or `unconfirmed`. Cancelling future authority does not acknowledge remote cleanup.

| Owner | Implementation and invariant |
| --- | --- |
| Handoff/report decisions | `src/delegation/background-handoff.machine.ts`: admission, observation, unavailable transport, explicit retry, expiry, cancellation, report delivery and exhausted recovery. Async observations carry the expected row revision; an old result/failure cannot advance a cancelled or resumed handoff. |
| Remote Stop obligation | `src/delegation/background-stop.machine.ts`: request, owned claim, acknowledgement, unavailable result and exhaustion. Each dispatch has a persisted attempt identity. Old acknowledgements cannot settle a newer attempt. |
| Acceptance lifetime | `background-admission.machine.ts` / `background-admission.ts`: prearm durable discovery, accept while that lease is fresh, then issue the immediate wake. A failed arm accepts nothing; losing the immediate wake cannot erase the prearmed lease. |
| RPC attempt lifetime | `background-attempt.machine.ts` / `background-attempt.ts`: claim, dispatch and correlated persistence in separate scoped stages. Effect scopes join owned local cleanup and preserve late defect/interrupt Causes. |
| Domain persistence | `background-mailbox.ts` and `adapters/background-mailbox.ts`: synchronous machine decisions stay inside the existing shared SQLite transaction. Report admission/acknowledgement and report Stop still share the conversation transaction. Native RPC work stays outside it. |
| Durable wake | `background-recovery.machine.ts` and `adapters/background-lifecycle.ts`: the existing `background-groups` capability and `background-groups:pump` job own discovery. The job retains the maximum prearmed lease after an early empty scan. Its fresh token fences terminal exhaustion inside the domain transaction; a newer same-ID admission cannot be failed by an older job callback. |

When family authority ends, the host still invokes reconciliation in cleanup-only mode: unfinished handoffs are revoked, pending Stops continue, and neither handoff dispatch nor report admission proceeds. The unit regression exercises an outage followed by successful Stop in that mode.

Stop uses at most five transport attempts within a five-minute policy window. Each claimed attempt has a thirty-second recovery lease; unavailable acknowledgements back off from two seconds, capped at sixty seconds. Exhaustion persists `unconfirmed`, leaves future execution unauthorized, and exposes an actionable error through the existing background projection. An explicit Stop may renew cleanup recovery without starting another group or report. Report transport retains its existing five-failure pause and original handoff deadline.

Start/Stop remote RPC observation is bounded at fifteen seconds. Native DO RPC cannot cancel already admitted remote work. `adapters/background-rpc.ts` therefore uses native `Effect.tryPromise` observation for those two remotely owned calls and stops observing at the deadline; a late reply cannot acknowledge the persisted attempt after the observation ended. It keeps a rejection handler attached. These calls own no local resource finalizers. The local native bridge and other native operations retain joined cleanup semantics; a deterministic held-cleanup test proves interruption waits for cleanup and retains its late defect.

Lifecycle retries a failing callback three times, with a 100 ms base delay and 1,000 ms cap. Its terminal handler pauses due handoffs or records due Stop obligations as unconfirmed, conditional on the current job token inside the shared transaction. It does not prematurely terminalize a still-leased Stop attempt. If storage also refuses the terminal write, the existing row remains intact and terminal persistence is logged as unconfirmed; the callback does not manufacture a committed outcome or renew an expired discovery budget. A still-fresh prearmed lease survives. Explicit retry/Stop and existing activation reconciliation remain recovery entry points after storage returns.

## Compatibility

The coordinated `20261023100524_outstanding_pixie` migration adds schema/workflow version 1, revision and Stop metadata. Existing cancelled rows become pending cleanup with immediate discovery and no initialized Stop deadline. The first actual claim establishes the finite policy window; rollout delay does not consume it. Existing group IDs, parent/conversation ownership, report IDs, immutable handoff contents, retry receipts and transport failure counts survive unchanged. Unknown schema/workflow versions and malformed machine events fail explicitly.

Remote group/Pi child execution and its own controls remain owned by their existing native group; this migration does not claim to migrate inventory B08 or replace that engine. The public background projection adds optional `stop` metadata and projects its actionable error. Activity keeps `Retry stop` available for pending or unconfirmed cleanup even after cancellation or report delivery. Its group/child labels say `Stop pending` or `Stop unconfirmed` instead of claiming acknowledged remote cleanup. The activity index places exhausted unconfirmed cleanup in attention and pending cleanup among active records. Stable `STATUS`/`STOP` handles likewise retain these cleanup obligations until acknowledgement; invoking the same handle calls the existing background Stop operation without restoring execution authority. These are integration corrections, not completion of the wider F14 lifecycle migration.
