# Send and inference latency

The October 19 production trace for a 1.40-second Send acceptance contained 988 ms in `Inference.discoverCatalog` and 1,110 ms in `Inference.readModelCatalog`. The complete admission operation took 1,130 ms. Its provider model-list fetch alone took 956 ms. This is a real production trace, not a simulated provider. Trace: `27e3de3ad1e1f93f3384f33616447a52`, starting `2026-10-19T22:05:39.546Z`, revision `7a2389d`.

## October 19 baseline changes (PR #174)

- Successful model capability metadata lasts five minutes instead of one. Live family membership and current credential identity are still checked on every read. Reconnection changes the cache key; failures are not cached and expired success is never a fallback. Remote readers still forward to the owner on every read. The tradeoff is up to five minutes of capability metadata age; this does not cache authorization. The first read after expiry still discovers models.
- Each existing family authority boundary reads the model owner and member in one joined SQL snapshot instead of two sequential D1 requests. No boundary or credential check is removed. Sixty native SQLite parity comparisons cover roles, verification, outsider isolation, owner changes, removal and reinvitation.
- The event pump publishes the leading change immediately, then coalesces the next 80 ms of changes. Previously it waited 80 ms before the leading change. The sliding queue, reader limits, authorization and cleanup remain in place.

## Measurement contract

`GET /api/agent/inference` includes optional `timings` on new settled attempts:

| Field | Offset from native stream admission |
| --- | --- |
| `fetchStartMs` | Provider transport invoked; local preflight has completed |
| `responseHeadersMs` | Provider fetch returns response headers |
| `firstEventMs` | First parsed provider event |
| `firstTextMs` | First nonempty `response.output_text.delta` |

Offsets use the same worker clock. Subtract `fetchStartMs` from `firstTextMs` for provider transport-to-first-text, including network and provider processing. An absent field means the milestone was not observed, not zero latency. Tool-only responses have no text milestone. These are numeric counters only: no response headers, tokens, prompts or text are stored. They are written with terminal usage, not on each token. Old and interrupted records may have no timings.

The existing attempt duration includes local preflight and final settlement; it is not provider time to first token. Browser Send-to-first-visible-text uses a separate monotonic clock and DOM observer. Do not subtract browser and worker wall clocks as if they were synchronized. Send acceptance uses the browser's request-to-response-headers resource timing. Compare the same agent, model, reasoning setting and prompt shape; report cold and warm catalog conditions and input/cache-token counts. Small live samples describe the observed runs, not a population percentile or guaranteed speedup.

The regression tests first reproduced repeated catalog discovery at 90 seconds and the mandatory 80 ms leading-stream delay, then passed with the fixes. Native provider tests verify that phase milestones survive the existing usage ledger without retaining prompt or credential contents.

## Account catalog reuse and refresh-ahead

This supersedes the hard five-minute expiry above.

The follow-up cache uses the account's persisted connection generation and the installed adapter capabilities as its identity. Token rotation retains that generation; reconnecting or replacing a deployment seed creates another. Legacy credentials acquire a generation lazily in the existing SQLite transaction. No new credential table or migration is needed.

Successful catalog snapshots are persisted in the account Durable Object. They are fresh for five minutes and reusable for up to one hour from the last successful verification. A stale read starts one scoped Effect refresh and immediately returns the snapshot. The host retains that work; disconnecting a reader does not cancel it. Restarts restore the same bounded snapshot. Transient failures retain success with exponential retry spacing capped at one minute; a hard-expired result is never served. Confirmed denial, invalid metadata, or an unclassified error replaces success with an unavailable result. Failure to persist a result blocks further reads in that runtime. Reconnect races cannot publish an old generation. Members still resolve the current owner and live membership on every read, with no independent cache on the member agent.

Catalog identity inspection does not resolve a token over the network. It can start account-owned refresh-ahead. Credential `expires` remains the usable-until time, already reduced by three minutes for safety; refresh-ahead starts five minutes before that. An otherwise valid token remains usable during an owned refresh. At usable-until it must join refresh before use. Failed or orphaned rotation intent blocks both metadata and credential reuse until reconnect; there is no refresh-token replay after an uncertain outcome. The existing owner serialization, persisted rotation intent, conditional commit and shutdown settlement remain in place.

The client model query uses `@tiesen/effect-tanstack-query` with TanStack Query and the Effect HTTP client. Its cache is scoped to the authenticated family workspace, keyed by agent, and cleared when that workspace unmounts. Mounted consumers share a request and refresh once a minute while active, which also provides an opportunity for OAuth refresh-ahead before Send. Settings changes cancel pending reads before mutation and invalidate after it; older responses cannot roll back a newer settings revision. Transport failures hide cached availability. The client cache never authorizes Send.

Neither background work nor cache warming guarantees a warm account after a long idle period. A missing or hard-expired catalog still requires discovery, and an expired token still requires refresh before inference. Acceptance and first-text timing must be measured separately; provider processing is unaffected by these changes.

## First text delivery

An October 20 production probe observed a 250,075-byte `MESSAGES_SNAPSHOT` for a nine-token response. Existing text growth used deltas, but adding the first assistant text message retransmitted the complete visible history.

When exactly one assistant text message is appended and every preceding message is unchanged, the adapter now emits TanStack's native `TEXT_MESSAGE_START` with the durable metadata and `TEXT_MESSAGE_CONTENT`. Subsequent text uses the existing delta path. Metadata changes, replacements, tools, deletions and reconnects still use authoritative snapshots. The existing scoped Effect stream owns publication, backpressure and cancellation.

Disabling SSE compression was tested in production in PR #183 but did not establish a latency improvement: five-chat median Send-to-visible-text was 4,893 ms before and 6,090 ms after, with variable provider time and one slow admission. Compression is restored; reducing first-text payload size is measured separately. These small sequential samples do not establish a percentile or a causal regression.

### Correlated first-text handoffs

The actor retains at most 32 volatile first-text records, containing IDs and clock readings only. The provider callback records `providerAt`; the native committed-event watcher records `nativeObservedAt`. The snapshot that first publishes an answer records `snapshotStartedAt`, `snapshotReadyAt` and `publishedAt`. Its TanStack batch includes a `durable-pi.first-text` custom marker, in the same queue slot as its regular frames and cursor. Historical reconnect snapshots do not claim to be a fresh first-text delivery.

The gzip website adapter observes that bounded marker without changing bytes. `Conversation.firstTextProxy` logs its `turnId`, `attemptId`, `publishedAt`, `proxyReceivedAt` and the first subsequent codec output read, `proxyOutputAt`. The latter is an output handoff bound, not proof that a particular compressed byte corresponds to a text token. It is available only on gzip responses. Oversized or malformed lines are ignored; conversation content is never logged. The browser measurement records marker receipt, first text receipt and first DOM appearance on its own monotonic clock.

Subtract actor milestones from each other, and proxy milestones from each other. Cross-machine wall-clock differences are diagnostic estimates, not precise one-way network measurements. Workers clocks advance on I/O; zero intervals do not prove zero CPU work. Missing native milestones remain missing rather than being inferred from publication. Diagnostics do not authorize, persist, retry or alter any model request.

A live CPU profile on the deployed revision identified a 263ms first-text render commit: unchanged timestamp formatting accounted for about 51ms of sampled CPU, and historical Markdown parsing also ran again. The shared Markdown component now memoizes its text prop; each delivery timestamp memoizes its unchanged date. Changed text and timestamps still render normally, and child state (including syntax highlighting) keeps its normal React lifecycle.

For an authenticated investigation, `events?protocol=tanstack&diagnostics=storage` adds `storageSyncStartedAt` and `storageSyncReadyAt` to first-text markers. This opt-in Effect joins `ctx.storage.sync()` after the first answer snapshot and before publication, so its duration measures outstanding write confirmation on the actor's clock. Ordinary streams do not add this wait. It does not change write confirmation policy, skip output gates, or expose a control in the UI. Use paired ordinary and diagnostic streams to distinguish storage confirmation from the remaining actor-to-proxy interval; cross-host clock differences still apply to that latter interval.

Paired production probes on October 21 returned immediately from `storage.sync()` while the marker still took roughly 0.47–1.49 seconds to reach the browser. This excludes pending writes at that checkpoint in those samples; it does not exclude writes begun afterward. The same opt-in diagnostic stream now logs `Conversation.firstTextGateway` at the intermediate Worker, with `gatewayReceivedAt`, `publishedAt`, `turnId` and `attemptId`. Join on both turn ID and publication timestamp because multiple clients can observe one turn. The observer adds a bounded stream reader only for diagnostic requests, forwards bytes unchanged, and joins upstream cancellation. Ordinary responses retain direct native forwarding. This separates the Durable Object-to-gateway interval from gateway-to-website receipt, subject to cross-host clock differences and the probe's additional reader.

The next diagnostic pass adds a unique `streamId` and `gatewayReadStartedAt` for each storage-probe stream. The read timestamp belongs to the read that completes the marker, so fragmented markers can span earlier reads. If this read began before actor publication, delayed downstream demand cannot explain its wait. The actor logs `Conversation.firstTextActor` after enqueue, with queue size/pull counters and four timer/confirmation samples (1, 25, 100 and 500 ms waits). The timer's requested/resumed readings expose scheduling progress; each subsequent `sync()` bounds pending write confirmation at that checkpoint. This scoped fiber is owned by the event stream and cancellation joins any in-flight uninterruptible confirmation. No write, SQL text or message content is recorded. An empty JS queue means the runtime has consumed bytes, not that network delivery completed. Frozen Workers clocks and cross-host estimates still limit attribution; use these observations with controlled comparisons rather than treating any single zero as absence of CPU work or later writes.

Storage probes also include an actor stream-open timestamp in a response header. The gateway records its clock immediately before forwarding and after receiving headers, then includes these three readings in the first-text log. If the clocks represent wall time with a stable offset, the actor-minus-gateway offset lies between `actorStreamOpenedAt - gatewayHeadersReceivedAt` and `actorStreamOpenedAt - gatewayRequestStartedAt`. Adding these bounds to `gatewayReceivedAt - publishedAt` gives a handoff range. A slow stream opening produces loose bounds. Runtime clock clamping can change the apparent offset between opening and publication, so even a narrow opening interval is not proof of exact network duration.

For a controlled small-frame buffering experiment, authenticated storage probes may add `padding=4k` or `padding=16k`. This prepends exactly 4,096 or 16,384 bytes of SSE comment to the first-text queue slot once per newly observed answer. Parsers ignore the comment; no message content or storage policy changes. All other values and ordinary streams receive no padding. Compare simultaneous control and padded streams for the same turn, matched by `streamId`, with clock-offset bounds. Padding is an experiment, not an established optimization or a default transport change.

### Timer clamping and query compilation

The workerd source adds a stronger qualification than clock freezing alone: [TimerChannel::now](https://github.com/cloudflare/workerd/blob/2e36a384412f6eb5ccec513635728041b5da9533/src/workerd/io/io-channels.h#L72-L82) allows production implementations to clamp observable time to the earliest active timer deadline, and [timer delivery](https://github.com/cloudflare/workerd/blob/2e36a384412f6eb5ccec513635728041b5da9533/src/workerd/io/io-context.c%2B%2B#L1033-L1104) observes the delivered deadline. Exact 1/25/100/500 ms readings therefore do not rule out CPU work, delayed scheduling, or input gating. Local workerd clocks differ from the hosted clock policy. Use the browser's monotonic Send-to-DOM measurement for the user experience and native CPU evidence for expensive functions; do not assign an entire cross-host timestamp gap to transport.

Live actor profiles identified Drizzle query construction and row-mapper creation as repeated work. A controlled real SQLite benchmark with 100 synthetic turns, alternating query modes and excluding the first two warmup rounds, measured median 52.8 ms rebuilding versus 18.3 ms reusing a prepared query per 1,000 member reads. These are local measurements, not a hosted chat speedup. The member reader now prepares its two fixed SQL shapes once per store instance, uses bound root IDs, and executes each read through the current Effect SQLite lease. It caches neither rows nor transaction state. Tests cover different roots, input visibility, newly admitted steers and rollback through the same prepared query.

The snapshot also reads membership for its visible roots in one SQL query, then groups those fresh rows by root while preserving sequence order. Previously it issued one membership query per displayed turn and another for each running turn. This removes up to 100 repeated reads per snapshot without introducing a history cache. One bound JSON keyset, expanded with `json_each`, keeps the query below Durable Object SQLite's 100-variable limit. Activity, reply-file and metadata reads retain their existing behavior. The regression covers 51 roots with steering, bulk-reader parity covers separate roots and empty/missing inputs, and native workerd verifies 48, 49 and 100 roots, input visibility, fresh prepared bindings and rollback.

Saved activity now also uses one bound keyset query and one existing Effect-owned transaction for the visible turns without a live observation. Previously, each saved activity read opened its own native transaction and Effect callback runtime: 100 historical turns meant 100 transactions. Live activity still takes precedence, missing rows stay absent, stored item order remains intact, and selected corrupt rows remain defects. The shared decoder caches only the schema interpreter; every read executes against the caller's current SQLite lease. The native regression checks 48, 49 and 100 keys, quoted IDs, exact single-reader parity, fresh rollback behavior, and the reduction from 100 transactions to one.

Reply-file links also use one bound keyset query instead of one query per visible turn. Distinct linked files are read once per snapshot, then grouped in the same per-turn operation order, with the existing readiness/trash checks and per-turn deduplication. No file content is read and no metadata survives the snapshot. Tests compare the single and bulk readers for 100 turns, duplicates, quoted and missing keys, outside-turn links, uploading files, trash and restore. Native workerd checks 48, 49 and 100 keys. A local real SQLite fixture with 100 completed turns and no reply files, alternating modes and discarding two warmup rounds, produced identical snapshots with 205 versus 7 reads and 101 versus 2 transactions; median snapshot time was 9.64 versus 2.69 ms. This establishes work reduction, not a hosted first-text speedup.

### Reader backpressure and complete publication

A paused-reader regression exposed a deterministic failure in the four-frame queue: an initial snapshot could leave insufficient capacity for the first-text marker, message start, text content and cursor. Publication then closed the stream partway through the update, forcing a reconnect before the answer became visible. A production chat with a premature reconnect and a 10.58-second Send-to-DOM time motivated the regression, but that observation alone does not establish the cause of its reconnect.

The adapter now enqueues each complete publication as one SSE batch. Effect waits for reader demand before reserving a slot; heartbeats skip a full queue or a reserved slot. The queue retains at most four batches, with the existing bounded state projection and sliding update notification. Cancellation interrupts the capacity wait and joins subscription/watch cleanup. The 60-second authorization deadline still closes a stalled stream. `Conversation.streamBackpressure` logs the first capacity wait per stream with a turn ID and queue size only. Unit regressions cover whole-answer delivery, paused-reader recovery, skipped heartbeats, cancellation and the deadline; native workerd also leaves the real adapter unread across first-text publication and verifies text, both cursors and joined cleanup. This proves the buffer defect and its fix, not the exclusive cause of every hosted handoff delay.

A second real SQLite benchmark compared the previous committed snapshot/store with this combined change on the same 100-turn fixture. Results were identical; read operations fell from 304 to 205 per snapshot. Alternating modes and excluding two warmup rounds, median local wall time fell from 13.7 to 8.7 ms per snapshot (about 36%). This isolates the application work saved; production Send-to-first-text still includes provider, scheduling and transport variation.

## Independent upstream observation (22 October)

An authenticated `GET /api/agent/events?agent=home&diagnostics=upstream` opens a one-shot probe for the next conversation inference attempt. Wait for its `ready` frame before sending. Only one probe can be active per actor; it expires after 60 seconds and is released on disconnect. Ordinary requests keep their existing provider fetch path.

The probe delegates the exact OpenAI Responses request to the internal `UpstreamRelay` WorkerEntrypoint. It owns the provider connection and emits `dispatch`, `headers`, and the first nonempty `response.output_text.delta` as `upstream-text`. Frames contain correlation IDs and stage names only. The relay accepts only POST requests to `https://api.openai.com/v1/responses`, follows no redirects, and exposes no public proxy handler. Request credentials stay within the existing Worker.

The provider reader must stay in the relay's context. A native tee exported to the actor failed the gated control: the supposed upstream observation arrived only when the actor resumed reading. The implemented Effect pump copies bytes into a bounded queue of four 16 KiB slices, retaining at most one additional transport chunk of at most 1 MiB. It preserves bytes, status and headers; larger chunks fail the diagnostic attempt. A separate RPC cancellation capability owns cancellation before headers and joins body cleanup. AbortSignal is not serialized. A separately owned three-second marker flush preserves slow-consumer observations without holding inference settlement.

Run `pnpm test:upstream-runtime` for actual workerd controls. An independent Node monotonic clock receives the probe and the actor response. The upstream sends text after 200 ms; a source-actor input gate or an unread actor body holds its response for 700 ms. The upstream marker must escape while that hold remains active. The same suite exercises abort before headers, body cancellation, and exact response preservation. Unit tests cover bounded read ahead and split, malformed and oversized SSE lines.

For production, record Send, probe receipt, ordinary first-text receipt, DOM insertion and the first frame containing text in the message viewport on one browser `performance.now()` clock. Match turn and attempt IDs. Keep probe-enabled samples separate from ordinary chats: the relay introduces a hop and bounded read ahead. Separate HTTP streams can have different delivery delays; negative intervals or missing markers are measurement limits, not evidence of zero work. Do not subtract actor clocks, console timestamps or custom-span timestamps to assign physical latency, and do not infer that co-arrival excludes CPU shared by both observations.

### Idle observer cleanup

An actual idle HTTP disconnect exposed a different case from cancelling a local body reader: the next observer could receive 429 until the unused lease expired. AgentWorker now enables `enable_request_signal`, as the Website already does. An Effect-owned SSE comment heartbeat surfaces an idle closed peer; it queues no additional comment while the body is backpressured. Reader cancellation and actor-owner release run concurrently through one idempotent cleanup, allowing the actor to abort its unused transferred writable. The native socket-abort/reopen regression fails without the cancellation flag or with the old cleanup and must reopen within 1.5 seconds. Claimed inference retains its normal deadline and caller cancellation.
