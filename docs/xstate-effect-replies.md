## Invariants and ownership

The existing email/WhatsApp message rows remain authoritative. The additive migration records schema/workflow version 1, a revision, send-attempt identity, claimed part index and recovery deadline. Existing message IDs, fingerprints, settings generations, retry receipts, frozen plans and provider receipts retain their values. Existing sending rows with no owner/deadline are recoverable as legacy uncertainty; complete receipt sets resolve to sent without a provider call. Unknown versions fail validation rather than resetting data.

`message.machine.ts` makes synchronous decisions inside the existing channel transaction. A new attempt claims a waiting row; the same owner can claim the next part only after the previous receipt commits. Checkpoints must extend the exact frozen plan and receipt prefix by one. A completed reply must identify its last saved receipt. Stale checkpoints, finalizers and completion events cannot alter a newer explicit retry. Authority and channel generation are checked again before each part; WhatsApp also checks its reply window.

`delivery.machine.ts` owns arming, claiming, sending, checkpointing and finishing. Before send intent commits, the production channel runner arms a separate recovery job in the existing Lifecycle owner. A claim whose armed deadline elapsed during authority lookup cannot commit. Each part has a 60-second recovery deadline; this is eligibility for reconciliation, not a claim that a remote provider stopped or that an alarm will run at an exact millisecond.

The delivery scope joins owned Effect work and resource cleanup before its owner-specific recovery finalizer runs. Each provider observation consumes the remaining committed send lease. Email binding RPC and remote WhatsApp RPC expose no local cancellation handle; observation can end with durable uncertainty while the remote send continues. Their late results cannot checkpoint the old attempt. Synchronous rendering/validation defects and complete active failure Causes remain distinct from provider rejection. A missing receipt becomes uncertain immediately, even while the same host remains alive. If all receipts committed but completion acknowledgement failed, recovery records sent. If immediate recovery also fails, the persisted deadline and prearmed job remain available. Regular channel pumps reconcile due attempts and include sending deadlines in their next-wake projection. Startup reconciliation can resolve every old attempt because its previous scope no longer exists.

Recovery never automatically resends an uncertain part. Explicit retry still requires duplicate-risk acknowledgement, preserves confirmed receipts and the frozen plan, and retains the existing retry limit and operation receipt. Provider rejection, uncertainty, cancellation, interruption and defects remain distinct. Compound failures and failed joined cleanup are retained. The deadline does not claim remote cancellation or exactly-once delivery.

`preparation.machine.ts` owns each bounded channel pass: authority/window check, task or approval control, media claim/import/checkpoint, native conversation admission, preparation checkpoint, turn observation, notification and reply delivery. Every invocation consumes the same persisted work deadline, including authority checks, media, native admission, observation and nested delivery preparation. An elapsed deadline cannot dispatch work; timeout joins owned cleanup and fails the pass without renewal. Remote RPC observation is interruptible, while local transactions and readers keep joined cleanup. Channel code supplies pure formatting/projections and Effect capabilities. The old imperative per-message progression and unrestricted status-update methods have been removed. Media completion/rejection uses the persisted reply revision to fence an obsolete import after a newer preparation or retry.

`admission.machine.ts` prearms discovery, accepts under a finite lease, then requests the immediate pump wake. Receive, notices and explicit retries use it; the stores reject fresh commits after the lease expires. A replay retains its original receipt. Approval-notice acceptance also checks that its parent remains waiting inside the same channel transaction, so a notice prepared before cancellation cannot appear afterward.

`recovery.machine.ts` stores schema/workflow version 1 and the latest prearmed deadline in the existing Lifecycle job payload. An early empty scan retains later admission leases. Observation records its clock **before** reading rows: an admission can commit while those reads are in flight, including when the lease expires before the scan finishes. A new same-ID queue push supersedes an old callback through native Lifecycle outcome fencing. No second alarm or workflow journal is introduced. Legacy payload-less jobs retain their original deadline; incompatible payloads/events fail validation.

`email/configuration.machine.ts` and `whatsapp/configuration.machine.ts` reconstruct versioned settings rows and decide exact replay, conflicts, revision/generation changes, cancellation and WhatsApp route updates. Disable cancellation remains atomic with settings changes and preserves sending ownership. Availability/authority prechecks in the application are request validation; durable progression belongs to these machines.

A separate `work_deadline` in each existing message row prevents an unrelated incoming message from reviving expired preparation work. Admission and explicit retry store their prearmed deadline; replay does not renew it. A successful owned pass or ordinary Pi waiting observation may prearm and renew the exact row revision. Failed, stale or no-op work cannot renew. The migration gives legacy queued/waiting rows one grace period measured at migration execution, without reset on restart. Sending retains its independent attempt lease.

The shared `ReplyRunner` preserves the `email`/`whatsapp` capability and job IDs. Lifecycle owns three job attempts, with 100 ms base delay and a 1,000 ms cap. After exhaustion, a domain-machine event conditionally makes queued/waiting replies failed, checking the current job token and peer ownership inside the same domain transaction; a due send becomes sent from complete receipts or uncertain otherwise. A still-live send keeps its owner/deadline. A failed reply can be retried explicitly using its existing message and native submission identities; recovery never authorizes a new provider action.

If the terminal domain write itself fails, the runner records the complete failure and retains any unexpired prearmed admission lease. Original domain rows remain. Status/startup reconciliation checks queue absence inside the domain transaction before terminalizing expired orphan work, and rearms existing jobs without replacing their identity or budget. Ordinary discovery also terminalizes expired work before deriving another wake, avoiding repeated immediate recovery that starves the pump. A new inbound job cannot renew an older expired row; only explicit retry can authorize fresh work. Whole-SQL failure must fail closed rather than treating an unreadable queue as absent. The combined native outage matrix passed on the frozen B01–B05 tree, with synthetic remote outcomes and the limits recorded below.
