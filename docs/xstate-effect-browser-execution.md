# Browser and Execution lifecycle migration (B09)

**Release status — 25 October 2026:** the refactor is [merged, deployed and verified](xstate-effect-release.md). The checkpoints below retain their original source and test scope; pre-merge delivery status is historical.

B09 replaces browser session/operation/retirement and code-run lifecycle decisions with the pinned official `@xstate/effect` integration. This candidate retains the existing browser and code-run ledgers, resource identities, Access decisions, network policy, and native execution limits. The public Browser and Execution APIs are unchanged. No SQL schema migration, provider action, merge, or deployment is part of this lane.

## Invariants and caller inventory

Before implementation, the Browser write paths were `BrowserStore.update/reset/transfer`, called by `BrowserWorkspace` admission, acquisition, publication, control, recovery, and cleanup. HTTP and Pi tools call that workspace; the agent worker calls startup recovery and Lifecycle maintenance. No provider result may publish after its generation, controller, or attempt is superseded. A confirmed rejection or failed load remains distinct from an uncertain interaction. Recovery never repeats input. A screen version identifies its capture; takeover, reset, and failed/interrupted operations clear stale captures. Absolute and idle expiry remain separate, and policy/controller changes retain generation fencing.

Execution writes were admission, finish/cancel, interruption, and recovery in `makeExecutions`, through the existing SQLite ledger. HTTP, Pi tools, and the execution worker consume that service. Only a fresh atomic claimant may invoke code. Repeated identity/content returns its retained receipt; conflicting content fails. Cancellation and a failed or missing result never authorize code replay. Run outcome and resource occupancy are independent: a terminal outcome does not release a slot before cleanup settles. The host must close admission before joining active work or disposing dependencies. Factory initialization also remains uninterruptible until its finalizer is registered, so direct construction cannot orphan a partially acquired actor.

Two baseline defects were reproduced before their correction. A browser result held across recovery returned success and restored the old capture. An Execution admission waiting behind SQLite could return a fresh running receipt after its host closed, leaving an accepted intent without a live owner. Independent review additionally reproduced an inherited browser acquisition leak: setting the local handoff flag inside an outer transaction dropped cleanup ownership if that transaction rolled back.

## Authoritative machines and native work

| Lifecycle | Machine decisions | Effect/native responsibility |
| --- | --- | --- |
| Browser session | `session.machine.ts`: begin, adopt, capture, failure, recovery, reset, takeover, and expiry/archive maintenance | Existing SQLite transaction reconstructs and advances versioned domain data. The retired-session ticket and session removal commit together. |
| Browser operation | `operation.machine.ts`: admission → acquisition when needed → dispatch → publication | The tab permit encloses the actor scope and all invoked work. Closing that scope joins native settlement and finalizers. The host retains complete late Causes after alpha.8 child interruption. |
| Browser connection | `connection.machine.ts`: connected → disconnecting after 30 seconds → closed | Puppeteer connection and its finalizer share one disconnect Promise; scope closure joins an already-started disconnect. This deadline does not delete durable session ownership. |
| Browser retirement | `retirement.machine.ts`: close → acknowledge, or retain ticket for retry | Both close and acknowledgement work are observed through joined scope cleanup. A typed close failure retains the existing ticket; a defect or interruption remains fatal. Lifecycle retains the 30-second maintenance retry and is the sole wake owner. |
| Code run | `run.machine.ts`: atomic admission, completion/cancellation/interruption, correlated resource release, and restoration | The existing `code_runs.record` is the sole record. Output publication compares attempt/revision; cleanup release compares its owning attempt. |
| Code execution | `driver.machine.ts`: authorize → execute → publish, or cancel | Effect owns the executor, request/body lifetime and joined cleanup. Native WorkerLoader CPU, network, output and time limits remain unchanged. |
| Execution host | `host.machine.ts`: open, failed, closing, closed | Its owner closes admission first, joins in-flight admission, closes the work scope, then closes the host scope. A full failed Cause is retained rather than reducing it to one error. |

Browser generation validation remains pure input/authority validation. Hostname/URL checking, screenshot byte-budget selection, masking/unmasking, CDP target lookup, interception callback draining, modifier-key release, and Puppeteer launch/connect protocol mechanics remain native Effect work, not additional application progression engines. The operation machine decides whether acquisition, input or publication is permitted. The local `adopted` resource flag transfers cleanup responsibility only after the outer SQLite transaction succeeds; it is not a second session status. Failed adoption retires the acquired session, and failed retirement storage still attempts immediate native close.

Execution's semaphore coordinates live resource installation and recovery; it does not replace the shared SQLite/Pi coordinator. The active fiber map stores live handles, not durable run status. Native code remains isolated with no outbound binding, zero subrequests, the existing CPU budget, bounded body/output, and the existing timeout. The authorization actor handoff is followed by an immediate dispatch check of current host/writable authority and the persisted status, attempt, revision and occupancy. Archive, cancellation, or recovery during that handoff suppresses native execution. There is no business retry or automatic replay of an interrupted/uncertain code run.

## Compatible restoration

Browser keeps the existing `bot_browser` JSON row and `retired_browsers` IDs. Its record adds `schemaVersion: 1`, `workflowVersion: 1`, and nullable `attemptId`; the existing `version` remains the capture/revision counter. Legacy records preserve controller defaults, restricted-policy defaults, session ID/target/deadlines, generation, version, content and screenshot. Legacy loading records acquire deterministic identity `legacy:<generation>:<version>`. Startup recovery revokes that attempt, records interruption and clears capture without dispatching a browser action. Future or partial versions fail explicitly. No independently writable machine snapshot is persisted.

Execution keeps the existing `code_runs` table and IDs. Its private record adds `schemaVersion: 1`, `workflowVersion: 1`, `attemptId`, `revision`, and `occupancy: { state, ownerId }`. Legacy running rows hydrate with `legacy:<run-id>` ownership and held occupancy; completed rows hydrate free. Recovery seals retained running code as interrupted without repeating it and releases stale ephemeral occupancy. Completed outcomes and immutable code/data survive. Unknown or partial versions fail rather than resetting storage. Compatibility is checked per decoded record: get/list/recovery reject incompatible rows, while the occupancy/count query does not globally freeze unrelated new IDs solely because an incompatible terminal/free row exists. Current running or held/blocked rows still fence admission through the existing SQL projection. Public receipts are projected through `CodeRun`, so internal ownership fields are not exposed by HTTP or tools.

Recovery requires exclusive Durable Object activation after the old host has ceased owning work. The only production call is `PersonalAgent.onStart()` in `src/agent/worker.ts`; its Execution/Browser services are readonly members of the one actor runtime. `makeExecutions`, ledger construction, and warm service facades do not call recovery. No HTTP or tool route exposes it. The installed Agents startup contract calls `onStart` before connections. Calling `recover()` on an independently constructed live peer is not a supported takeover mechanism and can release the old peer's ephemeral occupancy; the cross-host tests prove atomic admission and stale-result fencing, not that unsupported takeover. Parent integration retains this activation precondition.

These are versioned domain-data restorations, not persisted XState library snapshots. The library pins remain those established by the canonical standard; native Pi task implementation and existing execution resource identities are unchanged. Conversion is written on the next owning ledger mutation in the existing transaction. No generated SQL migration is required.

## Verification and limits

The focused Browser gate covers existing browser policy/control, native driver, boundary and Pi receipt/recovery tests plus deterministic B09 lifecycle witnesses. The new witnesses cover cross-host admission, stale results and stale cleanup after recovery/new captures, compatible and incompatible versions, malformed events, held invocation/acknowledgement cleanup, full late compound Causes, and real SQLite rollback during session adoption. Existing native-driver tests retain partial acquisition, CDP detach, close/disconnect, mask cleanup, native navigation uncertainty, and timer ownership coverage.

The focused Execution gate covers run identity, fresh claimant behavior, cancellation, limits/native boundary behavior, restoration, shutdown during a held SQLite admission, cleanup occupancy, stale release/publication and full late compound Causes. Independent Browser review confirmed both the retirement-acknowledgement Cause correction and the acquisition-commit ownership correction with fresh held-cleanup/rollback probes. A separate Execution reviewer reproduced the direct-factory partial-acquisition leak at scheduler budget 32 and verified the correction for direct and Layer construction at budgets 32, 64, 128 and 256.

Failure-sensitive controls remove the browser admission guard, drop browser late-Cause retention, remove acknowledgement observation, and move acquired-session ownership before commit. Each fails its targeted assertion; the source is restored byte-for-byte before the normal gate. Execution controls remove in-transaction host-close checks and late-Cause retention; each fails its corresponding regression. These controls demonstrate the named ownership properties, not exactly-once provider execution.
